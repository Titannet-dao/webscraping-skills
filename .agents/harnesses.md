# Harness compatibility

Every harness below reads the **same** `SKILL.md`. There is no per-harness copy of a
skill — only different directories to install the one copy into, plus one optional
sidecar file for Codex.

Sources for everything on this page are linked at the bottom. Verify against them
before changing anything here; do not edit this file from memory.

## Where each harness looks for skills

| Harness | Project-level | Global |
| --- | --- | --- |
| Claude Code | `.claude/skills/<name>/` | `~/.claude/skills/<name>/`, plus installed plugins |
| Codex | `.agents/skills/<name>/` (cwd, parent, repo root) | `~/.agents/skills/<name>/`, `/etc/codex/skills` |
| Cursor | `.agents/skills/<name>/` or `.cursor/skills/<name>/`, scanned recursively including nested project dirs | `~/.agents/skills/<name>/`, `~/.cursor/skills/<name>/` |
| Antigravity | `.agents/skills/<name>/` | `~/.gemini/config/skills/<name>/` |
| Gemini CLI | `.agents/skills/<name>/` (takes precedence) or `.gemini/skills/<name>/` | — |

`.agents/skills/` is the convergent project-level path: Codex, Cursor, Antigravity and
Gemini CLI all read it. Claude Code is the odd one out with `.claude/skills/`, but it also
installs skills via plugins, which is how this repo ships to Claude Code users.

Cursor also reads `.claude/skills/` and `.codex/skills/` for compatibility, and scopes a
skill found under a nested project directory to files inside that directory.

`scripts/link-skills.sh` symlinks every skill in `skills/` into all of these.

## `SKILL.md` frontmatter

Per the Agent Skills specification:

| Field | Required | Constraints |
| --- | --- | --- |
| `name` | yes | 1–64 chars, lowercase `a-z0-9` and `-` only. No leading/trailing hyphen, no `--`. **Must match the parent directory name.** |
| `description` | yes | 1–1024 chars. Says both *what it does* and *when to use it*. |
| `license` | no | License name, or the name of a bundled license file. |
| `compatibility` | no | ≤500 chars. Only if the skill has real environment requirements (`Requires git, docker, jq`). Most skills omit it. |
| `metadata` | no | Arbitrary string→string map for client-specific properties. |
| `allowed-tools` | no | Space-separated pre-approved tools, e.g. `Bash(git:*) Read`. Experimental; support varies by harness. |

Anything else is a harness-specific extension. Claude Code's
`disable-model-invocation` is one of these, and it has to sit at the **top level** —
Claude Code does not read it from under `metadata`.

That puts it outside the spec's field set, and the spec's own validator enforces that
set as closed:

```
$ npx skills-ref validate ./skills/titan-flow
  - Unexpected fields in frontmatter: disable-model-invocation.
```

This is expected for user-invoked skills, not a defect to fix. Real clients are laxer
than the reference validator — they ignore frontmatter they don't recognise, which is
what keeps one `SKILL.md` portable. Harnesses with no equivalent of the field simply
treat the skill as model-invoked, a graceful degradation rather than a load failure.
Codex is covered separately and properly by `policy.allow_implicit_invocation: false`
in `agents/openai.yaml`.

## Invocation: model-invoked vs user-invoked

Every skill is one or the other. It changes both the config **and** how the
`description` is written.

**Model-invoked** (the default) — reachable by the model or the user. Omit
`disable-model-invocation` and omit the `policy` block from `agents/openai.yaml`.
The `description` is *model-facing*: keep rich trigger phrasing ("Use when the user
wants…, mentions…, asks for…") so auto-invocation actually fires.

**User-invoked** — reachable only when a human types its name. Set
`disable-model-invocation: true` in the frontmatter (Claude Code) **and**
`policy.allow_implicit_invocation: false` in `agents/openai.yaml` (Codex). The
`description` becomes *human-facing*: a one-line summary someone reads while
browsing slash commands. Strip the trigger lists.

Keep the two settings in sync — a skill is user-invoked in both harnesses or in
neither. Reserve user-invoked for skills that are destructive, expensive, or that
only make sense when a human deliberately asks.

The test for staying model-invoked: *could the model usefully reach for this on its
own?* Reuse is a reason to extract a skill, not a reason to make it model-invoked.

## `agents/openai.yaml` (Codex sidecar)

Optional, and only read by Codex. It supplies picker metadata and the invocation
policy. Every key is optional:

```yaml
interface:
  display_name: "Human-readable name"
  short_description: "One line for the skill picker"
  icon_small: "./assets/small-logo.svg"
  icon_large: "./assets/large-logo.png"
  brand_color: "#3B82F6"
  default_prompt: "Optional surrounding prompt"

policy:
  allow_implicit_invocation: true # default; set false for user-invoked skills

dependencies:
  tools:
    - type: "mcp"
      value: "toolIdentifier"
      description: "Tool description"
      transport: "streamable_http"
      url: "https://..."
```

In this repo every skill carries one with at least `interface`, so Codex's picker
never falls back to a raw folder name.
